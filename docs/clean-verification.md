# 会社環境シミュレーション検証（事前クリーン検証）

## 1. 概要
自宅での開発環境では、ローカルで作成・生成されたファイルや `.gitignore` に含まれているファイルが作業ツリー上に存在するため、コードがそれらのファイルに依存していても自宅PCでは正常に動作してしまいます。
しかし、会社環境へは Git でコミットされた差分ファイルのみがパッチとして転送されるため、`.gitignore` で除外されていた設定ファイルや未コミットのファイルが会社PC上に届かず、「ファイルが存在しない」という実行時エラーが発生するリスクがあります。

この問題を未然に防止するため、自宅側でパッチを公開（push）する前に、**Git管理対象ファイルだけが存在する状態（＝会社側の状態）を基準に、ファイル欠落や公開できない差分がないかを自動検証する「会社環境シミュレーション検証」機能**を提供します。

---

## 2. 検証ロジック

### ① 会社へ届くファイルの確定
- 対象コミット（固定ブランチの先頭）の Git 追跡ファイル一覧を取得します（`git ls-tree -r <commit>`）。
- この一覧が「会社側に存在することになるファイル」の全体です。自宅PC上の `.gitignore` 対象ファイルや未追跡ファイルは含まれません。
- 作業ツリーで別のブランチをチェックアウトしていても、検証の基準は固定ブランチの内容です。

### ② ローカル重要設定ファイルの漏れ検知と誤検知防止
- 自宅のローカル作業ツリーを走査し、設定ファイル拡張子（`.json`, `.txt`, `.yaml`, `.yml`, `.toml`, `.ini`, `.conf` 等）を持つファイルを抽出。
- キャッシュ・ログ・ロックファイル（`__pycache__`, `.venv`, `node_modules`, `.` で始まるフォルダ, `*.log`, `*.db`, `indexes/`, `package-lock.json` 等）を除外した上で、**「ローカルに存在するが、Git追跡対象に含まれていない重要設定ファイル」**を検知。
- **テンプレートファイルの自動除外**:
  - Git追跡対象に `<path>.example`, `<path>.sample`, `<path>.template`, `<path>.default` が存在する場合、その実ファイル `<path>`（例: `backend/data/synonym_groups.txt`）は環境別設定ファイルとして自動的に欠落エラーから除外されます。
- **カスタム除外パターン (`clean_verify_ignore_patterns`)**:
  - 各リポジトリカードまたは設定で Glob パターン（例: `backend/data/*`, `config.json` 等）を指定することにより、意図的に Git 管理外にしている環境固有ディレクトリやファイルを柔軟に検証除外できます。
- 該当ファイルが存在する場合、次のようなエラーを報告し、公開を未然に防止します：
  > `重要設定ファイル 'backend/data/config.json' がローカルに存在しますが、.gitignoreまたは未コミットのためGit管理に含まれていません。会社環境でファイル不在エラーが発生します。`

### ③ 差分の公開可否チェック
直前の公開地点（`published_commit`、未公開なら `baseline_commit`）が設定されている場合、そこから対象コミットまでの差分について次を検査します。

- 直前の公開地点が固定ブランチの祖先であること（リベースや履歴の書き換えで祖先でなくなると、差分パッチを作成できません）
- 差分に、会社側が受け付けないパス（`.git` 配下を指すパスなど）が含まれないこと
- 差分にサブモジュールが含まれないこと（サブモジュールはパッチに含められません）
- 差分で届くファイルが、会社PC（Windows）で作れる名前であること
  - 予約名（`CON`、`PRN`、`AUX`、`NUL`、`COM1`〜`COM9`、`LPT1`〜`LPT9`。拡張子付きも含む）でないこと
  - 使えない文字（`< > : " | ? * \` と制御文字）を含まないこと
  - 名前の末尾が空白やピリオドでないこと
  - 大文字小文字だけが違う同名ファイルが無いこと（Windowsでは同じファイルになり、片方の内容が失われます）
- 差分のパス（追加・変更・削除のすべて）が、Windowsのパス長の上限に収まること
  - 会社側のリポジトリ位置（`C:\...` からリポジトリ直下まで）を **50文字**と仮定します（`COMPANY_ROOT_LENGTH`）
  - 適用中は、各ファイルを `.git/rep-patch/backups/<日時>/files/` へ退避するため、実体より約52文字長いパスができます。退避先を含めて259文字以内、フォルダは247文字以内であること
  - 結果として、リポジトリ内の相対パスは**156文字以内**が目安です。超えると公開を中断します
  - 削除するファイルも退避の対象なので数えます（`node_modules` のような深い入れ子の削除も止まります）

以前から存在していて今回の差分に含まれないファイルは、名前の検査の対象にしません。

### ④ 注意（warnings）
次のものは、公開を止めずに「注意」として表示します。カードの検証結果と、公開完了の通知で確認できます。

- **追跡されているのに `.gitignore` の対象でもあるファイル**: 会社側の同名ファイルを自宅の内容で上書きします。利用者ごとの設定ファイルを誤ってコミットした場合などに起きます。届けたくない場合は、そのアプリで `git rm --cached <ファイル>` を実行して追跡を外します。
- **Git LFS で管理されているファイル**（`.gitattributes` の `filter=lfs`）: 公開時に実体を取り出して同梱します（自宅側に `git-lfs` が必要で、実体を取得できないときは公開を中止します）。

### ⑤ 公開前リハーサルとの関係
この検証は、自宅側リポジトリの内容を調べるものです。作ったパッケージが会社側で実際に検証・適用できるかは、公開処理の中で別に確認します（[自宅側の運用](home-operation.md) の「公開前リハーサル」）。リハーサルは「検証をスキップして公開」を選んだ場合も必ず実行されます。

## 3. 画面操作・運用フロー

### ① ワンクリック事前検証
1. 自宅ダッシュボード上部のツールバーにある **「会社環境検証」** ボタンを押すと、登録された有効な全リポジトリが一括検証されます。
2. 特定のリポジトリだけを検証したい場合は、リポジトリカード内の **「検証」** ボタンを押します。
3. 検証結果：
   - **合格（OK）**: 緑色のバッジ `会社環境検証OK（設定ファイル欠落なし）` が表示されます。
   - **エラー検知**: 赤色の警告バッジおよび欠落しているファイル一覧が表示されます。
   - **注意**: 黄色の枠に内容が表示されます（合格でも表示されることがあります）。

### ② パッチ公開前の安全ガード & 即時リカバリ
- **「パッチを作成・公開」** ボタンを押した際、システムが自動的に事前検証を実行します。
- エラーが検知された場合でも、画面にエラー内容を表示するとともに「**会社環境シミュレーション検証でエラーが検知されました。検証をスキップしてパッチ作成・公開を強行しますか？**」という確認ダイアログが表示されます。
- 意図的な設定であることが分かっている場合は、OKを押すだけで即座に `skip_verification: true` で安全に公開を遂行できます。

## 4. API仕様

- `POST /api/repositories/{repo_id}/verify`
  - 指定リポジトリの会社環境シミュレーション検証を実行
  - 戻り値: `{ "valid": bool, "repo_id": str, "branch": str, "target_commit": str, "errors": list[str], "warnings": list[str], "checked_files": list[str] }`（`checked_files` は対象コミットの全追跡ファイル）
- `POST /api/home/verify-all`
  - 登録された有効な全リポジトリの一括検証を実行
  - 戻り値: `{ "all_valid": bool, "total_errors": number, "total_warnings": number, "results": { リポジトリID: 上記の検証結果 } }`
  - リポジトリを開けないなど検証自体に失敗した場合も、そのリポジトリの `errors` として返す
- `POST /api/home/publish`
  - リクエストボディ: `{ "skip_verification": false }`
  - 公開対象（有効で、未公開の変更があるリポジトリ）だけを検証し、検証エラー時はステータス 400 で公開を中断
