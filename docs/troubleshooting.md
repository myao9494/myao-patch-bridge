# トラブルシューティング

## 画面が開かない

1. `start_patch_app.bat` の黒い画面にエラーがないか確認します。
2. Edgeで `http://127.0.0.1:17345` を直接開きます。
3. ポート使用中の場合、ハンバーガーメニューのポートを変更して再起動します。
4. PWAだけを開いている場合は、先に `start_patch_app.bat` を実行します。

## VPN経由や別端末からアクセスできない

1. **待受ホストが `127.0.0.1` になっている場合**:
   - 画面左上のメニュー（☰）から設定ドロワーを開き、「待受ホスト」を `0.0.0.0` に変更して「設定を保存」した後に再起動します。
   - または、起動時に `--allow-vpn`（または `--host 0.0.0.0`）オプションを渡して起動します。このオプションはその起動の間だけ有効で、設定には保存されません。
     - Windows: `start_patch_app.bat --allow-vpn`
     - macOS: `./start_patch_app.command --allow-vpn`
     - 直接実行: `python -m rep_patch --allow-vpn`
2. **Tailscale MagicDNS（`*.ts.net`）でアクセスしたい場合**:
   - `data/settings.local.json` の `listen_host` が `0.0.0.0` に設定されていることを確認します（または設定ドロワーから変更）。
   - 起動時のコンソールログに `TailscaleアクセスURL: http://<マシン名>.<tailnet>.ts.net:17345/` が出力されます。
   - ブラウザでそのURLを開くことで、Tailscaleネットワーク内の端末から直接アクセスできます。
3. **アクセス元IPがブロックされている場合**:
   - セキュリティ保護のため、パブリックIPからの接続は403エラーで遮断されます。VPN（Tailscale、社内VPN等）または同一プライベートLAN（RFC 1918）内のIPアドレスから接続しているか確認してください。
4. **OSのファイアウォールでポートが閉じている場合**:
   - サーバー側マシンのファイアウォール設定で、TCPポート `17345` への受信通信が許可されているか確認してください。
5. **「このホスト名ではアクセスできません」と表示される場合**:
   - 安全のため、このアプリを指す名前以外のホスト名でのアクセスは遮断されます。IPアドレス、マシン名（ドットを含まない名前）、Tailscaleの `*.ts.net` 名はそのまま使えます。
   - 社内DNS名など上記以外のFQDNで開く場合は、設定の「待受ホスト」にそのFQDNを指定して保存し、再起動してください。


## pip installに失敗する

- Pythonが3.10以上か確認します。
- pipだけに許可されたインターネット経路が利用可能か確認します。
- `requirements.lock` を手動編集しないでください。
- ハッシュ不一致は配布ファイルの変更またはパッケージ取得経路の問題です。`--no-deps` や `--trusted-host` で回避しないでください。

## ZIPが一覧に出ない

- ファイル名が `myao_app_patch` で始まり、`.zip` で終わるか確認します。
- 既定フォルダは `%USERPROFILE%\Downloads` です。
- 別フォルダの場合はハンバーガーメニューから変更します。

## パスワードが異なる／改変エラー

自宅と会社で同じパスワードを設定してください。正しい場合はZIPを再ダウンロード・再移送します。マニフェストや分割ファイルを手動編集しないでください。

## ZIP内のファイルがありません（`packages/…/added_files/…`）

- **原因**: マニフェストに載っている同梱ファイルが、ZIPに入っていません。旧バージョンの自宅側アプリでは、アプリの `.gitignore` の対象でもある追跡ファイル（例: `backend/settings.local.json`）が、パッチ専用リポジトリへのコミットから漏れていました。同梱した `.gitignore` が、パッチ専用リポジトリの中でも働くためです。
- **会社側への影響**: ZIP全体が検証で拒否されるので、どのアプリにも適用されていません。会社側のリポジトリは変わっていません。
- **対処**: 自宅側の Patch App を最新にします。最新版はパッケージ内のファイルを強制的にコミットへ含め、さらに公開前リハーサルで同じ問題を検出して公開を中止します。届かなかったZIPは、自宅側のパッチ専用リポジトリで漏れたファイルを追加してpushし直せば、同じ連番のまま使えます。

  ```bash
  git status --ignored --porcelain
  ```

  `!! packages/…/added_files/…` と表示されたファイルが漏れているファイルです（`.DS_Store` は対象外です）。表示されたパスを1つずつ指定して追加します。

  ```bash
  git add -f packages/file_manager/000006/added_files/backend/settings.local.json
  ```

  ```bash
  git commit -m "Repair patch package"
  ```

  ```bash
  git push
  ```

## 自宅側で「公開前リハーサル…で問題が見つかったため、公開を中止しました」と表示される

会社側で失敗するパッケージを、pushの前に検出しました。パッチ専用リポジトリは公開前の状態へ戻っており、GitHubへは何も送られていません。メッセージの後半に、問題のあったアプリとパスが表示されます。

| メッセージ | 原因と対処 |
| :--- | :--- |
| `ZIP内のファイルがありません: …` | 同梱ファイルが「Download ZIP」に入りません。アプリの `.gitattributes` に `export-ignore` があると、GitHubのZIPからそのファイルが除かれます。該当の指定を外します |
| `追加ファイルが破損しています: …` | 同梱ファイルの内容がZIPの中で変わっています。アプリの `.gitattributes` の `working-tree-encoding` や `ident`、改行コードが混在したファイルへの `eol` 指定が原因です |
| `適用できません: …` | 会社側の適用処理が失敗しました。続くメッセージが会社側で表示されるはずだったエラーです |
| `適用後の内容が公開先コミットと一致しません: …` | 適用はできましたが、表示されたパスの内容が公開先コミットと違います。大文字小文字を区別しないファイルシステムで同名になるパスなどが原因です |
| `自宅側のリポジトリが登録されていないため、適用を確認できません` | パッチ専用リポジトリに、登録を消したアプリのパッケージが残っています |

## 追加ファイルが破損しています（Obsidianプラグイン等で「ファイルが壊れています」と出る）

- **原因**: Obsidianプラグインの設定ファイル（`manifest.json` 等）やテキストファイルが自宅側でCRLFで作成されていた場合、GitHub経由（「Code → Download ZIP」）でのダウンロード時にGitの自動改行コード正規化（LFへの変換）が働き、マニフェスト署名時のハッシュとZIP内実体のハッシュが食い違って破損と誤判定されることが原因です。
- **対処・仕組み**:
  - 最新の Patch App では、改行コードの差異（CRLF ↔ LF）を自動検知し、ファイル破損ではなく改行コード差異である場合は透過的に元バイト列を復元して適用を継続します。
  - また、パッチ専用リポジトリの `.gitattributes` に `packages/** binary` が自動設定され、Gitによる改行コード改変自体が根本防止されています。
  - 最新の Patch App への更新、または最新パッチの再ダウンロードを行ってください。

## パッチ連番が欠けている（`必要: 000003、検出: 000005` など）

パッチ専用リポジトリの最新コミット（＝「Download ZIP」）には最新の連番だけが入っています。自宅側で複数回公開する間に会社側の取り込みを飛ばすと、間の連番が手に入らず、このエラーになります。次のいずれかで復旧します。

- **間の連番のZIPが残っている場合**: 自宅側の公開のたびに生成される今回分ZIP（`myao_app_patch_日時.zip`、GitHub Releasesのアセットにも同じもの）を古い順に持ち込み、1つずつ適用します。
- **残っていない場合**: 自宅側で対象カードの「リセット」を実行し、「会社の初期導入地点」を会社側が現在持っている内容に相当するコミットへ合わせてから公開し直します。会社側では対象カードの「開始番号設定」で `1` を指定してから適用します（[自宅側の運用](home-operation.md) の「パッチ履歴のリセット」）。

会社側の内容が既にその連番相当まで進んでいると分かっている場合は、「開始番号設定」で次に適用する連番を直接指定できます。

## 「未コミットの変更があります」で適用・コミットが止まる

適用の前後でコミットしても作業ツリーがクリーンにならない場合に表示されます。次を確認してください。

- 適用中に、そのアプリ自身やエディタがGit管理対象のファイルを書き換えていないか（アプリを終了してから再実行）
- サブモジュール内に未コミットの変更がないか
- `.gitattributes` や `core.autocrlf` の設定により、コミット直後のファイルが常に変更扱いになっていないか（VS Codeで開いて差分を確認）

失敗したアプリは適用前の状態へ復元されています。原因を解消してから「このアプリに適用」を押してください。

## 自宅側で「パッチ専用リポジトリに未コミットの変更があります」と表示される

パッチ専用リポジトリに、Patch App以外が作成・変更したファイルがあります。Patch Appは公開に失敗しても作りかけのファイルを残さないため、表示された場合は手作業で置いたファイルや編集途中の変更が原因です。パッチ専用リポジトリで `git status` を確認し、不要なら削除、必要ならコミットしてから再実行してください。

## 一部アプリだけ失敗した

他のアプリは正常に処理されています。エラー内容を直し、「このアプリだけ再実行」を使用します。失敗したアプリは適用前の状態へ復元されており、同じZIPをそのまま再適用できます。

## 設定ファイルを読み込めない

`data/settings.local.json` が壊れている（手編集でJSONの書式を崩したなど）場合、画面にエラーが表示されます。ファイルを修正するか、退避してから起動し直して設定し直してください。BOM付きUTF-8で保存されたファイルはそのまま読み込めます。

## Gitバージョン・互換性が不明

「会社環境診断」を実行してください。日本語パス、CRLFテキスト、バイナリファイルの上書き配置・削除と、そのコミットを一時リポジトリで実際に検証します。診断に失敗したGitでは本番適用しないでください。
