# 自宅側の導入・運用

## 初回導入

```bash
cd /Users/mine/000_work/app/myao-patch-bridge
uv sync --extra dev
cd frontend
npm install
npm run build
cd ..
uv run patch-bridge
```

ハンバーガーメニューで「自宅」を選び、次を設定します。

```text
アプリルート
/Users/mine/000_work/app

Obsidian設定リポジトリ
/Users/mine/000_work/obsidian_setting_myao

パッチ専用リポジトリ
/Users/mine/000_work/myao_app_patch
```

パッチ検証パスワードは会社側と同じ値を設定します。パスワード変更後は既存パッケージを検証できなくなるため、最初の公開後は変更しないでください。

設定は `data/settings.local.json` に保存され、Gitには入りません。

## リポジトリ登録と選択

### 自動検出による登録
1. 「再検出」を押します。
2. 設定されたアプリルート直下のGitリポジトリとObsidian設定が自動で一覧化されます。

### 手動でのリポジトリ追加
1. 「＋ リポジトリを追加」ボタンを押します。
2. モーダルにGitリポジトリのパス（例: `/Users/mine/000_work/app/my-app`）を入力します。
3. 表示名、種類（通常アプリ / Obsidian設定）、固定ブランチ、初期導入地点、会社環境検証の除外パターンを設定し、「リポジトリを追加」を押します。

リポジトリIDは表示名から自動で決まります。同じIDのカードが既にある場合は追加できません（既存カードの公開済み地点や連番を上書きしないため）。別の表示名を指定するか、既存のカードを削除してから追加してください。

### リポジトリカードの削除（管理対象からの除外）
1. 不要なリポジトリカードの右上にあるゴミ箱アイコン（削除ボタン）を押します。
2. 確認ダイアログで「OK」を選択すると、管理対象から除外されます（※ローカルのファイルやGitリポジトリ自体は削除されません）。

### パッチ公開対象の選択
1. 各カードのスイッチをON/OFFして、パッチ公開対象を選択します。
2. ツールバー下の「すべて選択」「すべて解除」ボタンで一括切り替えも可能です。
3. リポジトリごとに固定ブランチ、「会社の初期導入地点」、会社環境検証の除外パターンを設定し、「この設定を保存」を押します。

### Antigravityで開く
各カードの「Antigravityで開く」ボタンを押すと、ワンクリックでローカルのAntigravity（Antigravity IDE）が起動し、対象リポジトリのワークスペースを直接開くことができます。

### パッチ履歴のリセット（#000001からの再作成）
パッチ公開済みのリポジトリをゼロからやり直したい場合に使用します。
1. 対象リポジトリカードの下部にある「リセット」ボタンを押します。
2. リセット確認モーダルが表示されます：
   - パッチ専用リポジトリ（リモート含む）から既存の全パッチファイルが削除されます。
   - 次回のパッチ作成番号は **#000001** にリセットされます。
   - 公開済みコミットの記録がクリアされます。
   - **初期導入地点の更新オプション**: 「現在の最新コミットを会社の初期導入地点にする」にチェックを入れると、現在のHEADを初期導入地点として再スタートできます。チェックを外したままの場合は、既存の初期導入地点からの差分として次回 `#000001` が作成されます。
3. 「パッチ履歴をリセット」を押すと、パッチ専用リポジトリの更新・コミット・リモートpush、およびローカル設定の初期化が自動実行されます。
   - パッチ専用リポジトリに未コミットの変更がある場合は、リセットを実行しません。先に内容を確認して片付けてください。
※会社側PCでもこのリセットに対応する際は、会社側カードの「開始番号設定」で次回適用番号を `1` に指定してください。

`myao-patch-bridge` 自身は自動検出対象から除外されます。
初期導入地点には、コミットID、タグ、ブランチ名を入力できます。保存時に完全なコミットIDへ解決されます。会社側のコミットIDは入力しません。

## 週次運用

1. 各アプリの固定ブランチへ変更をコミットします。
2. Patch Appで「更新」を押し、未公開コミット数を確認します。
3. 「パッチを作成・公開」を押します。
4. Patch Appが会社環境シミュレーション検証を行い、差分を生成して `myao_app_patch` にコミットします。
5. Patch Appが公開前リハーサル（下記）を行い、通った場合だけpushします。
6. push成功時だけ公開済み地点が進みます。

公開の前に、有効な全リポジトリの設定（初期導入地点が設定済みか、公開済み地点が固定ブランチの祖先か）を確認します。1つでも不備があれば、何も書き出さずに中断します。会社環境シミュレーション検証でエラーが出た場合は、内容を確認したうえで「検証をスキップして公開」を選べます（[会社環境シミュレーション検証](clean-verification.md)）。

### 公開前リハーサル

会社PCで起きるエラーを、pushする前に自宅で起こすための仕組みです。コミットした内容からGitHubの「Code → Download ZIP」と同じZIPを作り、会社側と同じプログラムで次を実行します。

1. ZIPの検証（署名、分割パッチ、同梱ファイル実体のサイズとSHA-256）
2. 「適用前の会社側リポジトリ」を一時フォルダへ再現し、パッチを実際に適用
3. 適用後の内容が、公開先コミットの内容と1バイトも違わないことを確認

問題が見つかると「公開前リハーサル…で問題が見つかったため、公開を中止しました」と表示され、コミットは取り消されます。GitHubへは何も送られず、連番も進みません。原因を直してからもう一度「パッチを作成・公開」を押してください（[トラブルシューティング](troubleshooting.md)）。この確認は省略できません。

公開完了の通知に「注意」が表示されることがあります。公開は完了していますが、内容を確認してください。

- **追跡されていますが .gitignore の対象でもあるファイルです**: アプリの `.gitignore` に書かれているのにコミットされているファイルです。会社側の同名ファイルを自宅の内容で上書きします。利用者ごとの設定ファイルなど、届けたくないものであれば、そのアプリで `git rm --cached <ファイル>` を実行して追跡を外してください。
- **Git LFS で管理されているため…**: 公開時にLFSの実体を取り出して同梱します。自宅側のリポジトリに `git-lfs` を導入し、`git lfs pull` で実体を取得しておいてください。取得できない場合は、ポインタを運ばずに公開を中止します。

公開処理では、前回地点から今回地点までの差分について以下を実行します。

- **変更・新規ファイル実体同梱**: 差分で新規追加または変更されたファイルの実体（テキスト・バイナリ問わず）を `added_files/` フォルダへ抽出し同梱します。会社側はこの実体を直接上書き配置します。リネームは「旧パスの削除＋新パスの追加」として扱います。
- **差分パッチ本体**: `git diff --binary --full-index <前回地点> <今回地点>` の出力も同梱します（パッケージ形式の互換性のため。20 MiBを超える場合は自動分割）。
- **削除ファイル記録**: 削除されたファイルをマニフェストへ記録し、会社側での確実な消去を保証します。大文字小文字だけを変えた名前変更（`claude.md` → `CLAUDE.md`）では、古い名前を記録しません（会社PCでは新旧が同じファイルを指すため）。
- **リポジトリ軽量化（最新パッチのみ保持）**: 過去のパッチディレクトリをワーキングツリーから自動削除し、今回作成されたパッチと今回分 `package-index.json` のみをコミット＆pushします。これにより、会社PCで「Code → Download ZIP」を実行した際のダウンロードサイズが常に数KB〜数MBの最小サイズに保たれます。
- **安全な連番カウントアップ**: 自宅側のローカル設定（`settings.local.json`）で各リポジトリの最新連番（`last_sequence`）を記憶するため、リポジトリから過去フォルダが削除されても次回パッチの連番は狂わず正常にカウントアップされます。
- **今回分軽量ZIPの生成**: 今回作成されたパッチのみを含む `myao_app_patch_*.zip` を、ダウンロードフォルダ（設定ファイルの `download_dir`、既定は `~/Downloads`）に自動生成します。`download_dir` が空の場合はパッチ専用リポジトリ内の `dist/` に出力します。ZIPの生成に失敗しても公開自体は完了しており、失敗理由が通知に表示されます。
- **GitHub Releases 自動公開**: 設定画面で `GitHub トークン (PAT)` が登録されている場合、GitHub Releases へ新規リリースを作成し、生成した今回分軽量ZIPをアセットとして自動アップロードします（Releases利用環境向け）。

### GitHub Releases 自動公開の設定（任意）
1. 左上メニュー（☰）の「設定」を開きます。
2. 「GitHub トークン (Releases自動公開用)」に、GitHub の Personal Access Token（権限: `Contents: Read and write`）を入力します。
3. 「GitHub リポジトリ名」が空の場合は、パッチ専用リポジトリの `origin` リモートから自動解決されます（例: `myao9494/myao_app_patch`）。
4. 「設定を保存」を押します。
以降、「パッチを作成・公開」を押すだけで、GitHub Releases へ自動的に最新ZIPが公開されます。
※トークン未設定の場合でも、ローカルに今回分ZIPが生成されるため、手動でReleasesにアップロードしたりUSBメモリで持ち出すことが可能です。


## 公開が途中で失敗した場合

パッケージの書き出し中に失敗した場合、作りかけのファイルは自動で破棄され、パッチ専用リポジトリは直前のコミットの状態へ戻ります。原因を解消して、もう一度「パッチを作成・公開」を押してください。

## push失敗時

パッチ専用リポジトリにはローカルコミットが残ります。次回の公開操作で、先に未pushコミットのpushを再試行し、成功すれば公開済み地点も追いつきます。ファイルを手動削除したり、コミットを書き換えたりしないでください。

pushは認証情報の入力待ちでは止まりません（入力が必要な状態なら失敗として戻ります）。パッチ専用リポジトリは、あらかじめ通常の `git push` が入力なしで成功し、upstreamが設定された状態にしてください。

## 会社側で問題が見つかった場合の修正

会社側では適用と同時にコミットが確定します。自宅では通常どおり修正を固定ブランチへコミットし、次の連番のパッチを公開してください。会社側は通常の手順で適用するだけです。

## 起動オプション

```bash
uv run patch-bridge --allow-vpn      # この起動の間だけVPN/LANからの接続を許可
uv run patch-bridge --port 18000     # この起動の間だけポートを変更
uv run patch-bridge --no-browser     # ブラウザを自動で開かない
```

起動オプションによる待受設定は設定ファイルへ保存されません。常にVPN/LANから使う場合は、設定ドロワーの「待受ホスト」を変更して保存します。
