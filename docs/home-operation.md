# 自宅側の導入・運用

## 初回導入

```bash
cd /Users/mine/000_work/app/myao-patch-bridge
uv sync --extra dev
cd frontend
npm install
npm run build
cd ..
uv run patch-bridge
```

ハンバーガーメニューで「自宅」を選び、次を設定します。

```text
アプリルート
/Users/mine/000_work/app

Obsidian設定リポジトリ
/Users/mine/000_work/obsidian_setting_myao

パッチ専用リポジトリ
/Users/mine/000_work/myao_app_patch
```

パッチ検証パスワードは会社側と同じ値を設定します。パスワード変更後は既存パッケージを検証できなくなるため、最初の公開後は変更しないでください。

設定は `data/settings.local.json` に保存され、Gitには入りません。

## リポジトリ登録と選択

### 自動検出による登録
1. 「再検出」を押します。
2. 設定されたアプリルート直下のGitリポジトリとObsidian設定が自動で一覧化されます。

### 手動でのリポジトリ追加
1. 「＋ リポジトリを追加」ボタンを押します。
2. モーダルにGitリポジトリのパス（例: `/Users/mine/000_work/app/my-app`）を入力します。
3. 表示名、種類（通常アプリ / Obsidian設定）、固定ブランチ、初期導入地点を設定し、「リポジトリを追加」を押します。

### リポジトリカードの削除（管理対象からの除外）
1. 不要なリポジトリカードの右上にあるゴミ箱アイコン（削除ボタン）を押します。
2. 確認ダイアログで「OK」を選択すると、管理対象から除外されます（※ローカルのファイルやGitリポジトリ自体は削除されません）。

### パッチ公開対象の選択
1. 各カードのスイッチをON/OFFして、パッチ公開対象を選択します。
2. ツールバー下の「すべて選択」「すべて解除」ボタンで一括切り替えも可能です。
3. リポジトリごとに固定ブランチと「会社の初期導入地点」を設定し、「この設定を保存」を押します。

### Antigravityで開く
各カードの「Antigravityで開く」ボタンを押すと、ワンクリックでローカルのAntigravity（Antigravity IDE）が起動し、対象リポジトリのワークスペースを直接開くことができます。

### パッチ履歴のリセット（#000001からの再作成）
パッチ公開済みのリポジトリをゼロからやり直したい場合に使用します。
1. 対象リポジトリカードの下部にある「リセット」ボタンを押します。
2. リセット確認モーダルが表示されます：
   - パッチ専用リポジトリ（リモート含む）から既存の全パッチファイルが削除されます。
   - 次回のパッチ作成番号は **#000001** にリセットされます。
   - 公開済みコミットの記録がクリアされます。
   - **初期導入地点の更新オプション**: 「現在の最新コミットを会社の初期導入地点にする」にチェックを入れると、現在のHEADを初期導入地点として再スタートできます。チェックを外したままの場合は、既存の初期導入地点からの差分として次回 `#000001` が作成されます。
3. 「パッチ履歴をリセット」を押すと、パッチ専用リポジトリの更新・コミット・リモートpush、およびローカル設定の初期化が自動実行されます。
※会社側PCでもこのリセットに対応する際は、会社側カードの「開始番号設定」で次回適用番号を `1` に指定してください。

`myao-patch-bridge` 自身は自動検出対象から除外されます。
初期導入地点には、コミットID、タグ、ブランチ名を入力できます。保存時に完全なコミットIDへ解決されます。会社側のコミットIDは入力しません。

## 週次運用

1. 各アプリの固定ブランチへ変更をコミットします。
2. Patch Appで「更新」を押し、未公開コミット数を確認します。
3. 「パッチを作成・公開」を押します。
4. Patch Appが差分を生成し、`myao_app_patch` にコミットしてpushします。
5. push成功時だけ公開済み地点が進みます。

公開処理では以下を実行します。

```text
git diff --binary --full-index <前回地点> <今回地点>
```

- パッチが20 MiBを超える場合は自動分割します。バイナリ、追加、削除、リネームも対象です。
- **新規追加ファイル実体同梱**: コミット差分で新規追加されたファイルの実体（テキスト・バイナリ問わず）を `added_files/` フォルダへ自動抽出し同梱します。
- **削除ファイル記録**: 削除されたファイルをマニフェストへ記録し、会社側での確実な消去を保証します。
- **リポジトリ軽量化（最新パッチのみ保持）**: 過去のパッチディレクトリをワーキングツリーから自動削除し、今回作成されたパッチと今回分 `package-index.json` のみをコミット＆pushします。これにより、会社PCで「Code → Download ZIP」を実行した際のダウンロードサイズが常に数KB〜数MBの最小サイズに保たれます。
- **安全な連番カウントアップ**: 自宅側のローカル設定（`settings.local.json`）で各リポジトリの最新連番（`last_sequence`）を記憶するため、リポジトリから過去フォルダが削除されても次回パッチの連番は狂わず正常にカウントアップされます。
- **今回分軽量ZIPの生成**: 今回作成されたパッチのみを含む `myao_app_patch_*.zip` をダウンロードフォルダ（または `dist/`）に自動生成します。
- **GitHub Releases 自動公開**: 設定画面で `GitHub トークン (PAT)` が登録されている場合、GitHub Releases へ新規リリースを作成し、生成した今回分軽量ZIPをアセットとして自動アップロードします（Releases利用環境向け）。

### GitHub Releases 自動公開の設定（任意）
1. 左上メニュー（☰）の「設定」を開きます。
2. 「GitHub トークン (Releases自動公開用)」に、GitHub の Personal Access Token（権限: `Contents: Read and write`）を入力します。
3. 「GitHub リポジトリ名」が空の場合は、パッチ専用リポジトリの `origin` リモートから自動解決されます（例: `myao9494/myao_app_patch`）。
4. 「設定を保存」を押します。
以降、「パッチを作成・公開」を押すだけで、GitHub Releases へ自動的に最新ZIPが公開されます。
※トークン未設定の場合でも、ローカルに今回分ZIPが生成されるため、手動でReleasesにアップロードしたりUSBメモリで持ち出すことが可能です。


## push失敗時

パッチ専用リポジトリにはローカルコミットが残ります。次回の公開操作で、先に未pushコミットのpushを再試行します。ファイルを手動削除したり、コミットを書き換えたりしないでください。

パッチ専用リポジトリは、あらかじめ通常の `git push` が成功し、upstreamが設定された状態にしてください。

## テスト不合格時の修正

会社では不合格パッチを未コミットのまま保持します。自宅では通常どおり修正を固定ブランチへコミットし、次のパッチを公開します。会社側で「修正パッチを重ねる」を使用します。

会社側で不合格パッチを破棄した場合、その後の増分パッチは適用できません。この場合は初期導入地点・公開済み地点の再設定を伴う復旧が必要です。
